# Username and public-Journal flag schema

Both the `username` field and the `journalIsPublic` flag land on the existing `user` table rather than a new settings table — there's only one boolean and one string being added, and no other account-level settings exist yet to justify carving out a separate table for them. `username` is added via Better Auth's `username` plugin (registered in `src/lib/auth/index.ts`), which itself contributes both a normalized `username` column (unique, lowercase) and a cosmetic `displayUsername` column preserving original casing; the columns are hand-added to `src/lib/db/schema/auth.ts` per issue #7's research, since Better Auth's Drizzle adapter expects the schema to already declare them. Neither column exists yet as of this decision — this is a new addition, not an amendment to prior work.

`username` is nullable (per the map's standing decision that username collection is deferred, not forced on registration), constrained to 3–20 characters of `a-z0-9_`, and checked against a reserved-word denylist (`journal`, `register`, `sign-in`, `api`, plus anticipated `lists`, `login`, `settings`, `admin`) at write time — app-level validation, not DB-enforced, since Better Auth's plugin provides neither reserved-word protection nor length/charset constraints itself. `journalIsPublic` defaults to `false` and may only be flipped to `true` when `username` is non-null; that invariant is enforced at the mutation layer rather than a DB constraint, and is the concrete trigger point for "prompt for a username only when first needed."
