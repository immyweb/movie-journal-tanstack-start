# List and ListItem schema

`List` is a new, single-owner, named collection of `Movie` references, distinct from `JournalEntry`: it deliberately carries no per-user watch data (rating, review, dateWatched), only a `Movie`. `ListItem` joins `List` to `Movie` and, unlike `JournalEntry` (which allows multiple entries per Movie per user to support rewatches), disallows duplicates — a Movie can only appear once per List. That asymmetry is enforced structurally with a composite primary key `(listId, movieId)` on `ListItem` rather than a surrogate id plus a unique constraint, since nothing ever needs to reference a `ListItem` by its own identity.

`List.shareToken` is the unguessable value a public share link is built from — generated with `crypto.randomUUID()`, the same mechanism this codebase already uses for `JournalEntry.id`, rather than pulling in a new id-generation dependency for the sake of a shorter token. It's `unique().notNull()` with an index, since it's the lookup key for the public share route (issue #11 decides the route shape itself). `List` cascade-deletes on both its owner (`userId`) and, per `ListItem`, on the referenced `Movie` — mirroring `JournalEntry`'s existing cascade behavior on those same two relations, even though ADR 0010 means a `Movie` row is never actually deleted by today's app logic; the cascade is declared for schema correctness in case that ever changes, not because it currently fires.
